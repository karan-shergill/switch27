# FeedBack

1. **Requirements**
    1. When listing non-functional requirements, prioritize the 3 to 5 that most directly affect the core user experience. A focused list signals to interviewers that you understand what actually matters for the system, rather than listing every possible concern.
2. **High Level Design**
    1. For leaderboard scoring in a contest system, always state the ranking rule explicitly during your design. For example, say users are ranked by number of problems solved, then by earliest accepted submission time as a tiebreaker. This makes it clear how the sorted set key or score is calculated and prevents ambiguity about who ranks first.
    2. Redis sorted sets are the go-to structure for real-time leaderboards because they maintain order by score automatically and support O(log N) insertions and rank lookups. Pair this with Server-Sent Events (SSE) to push live ranking updates to clients without requiring them to poll.
3. **Deep Dives**
    1. To block user code from making outbound network calls, run the Docker container with no network interface attached at all. You do this by passing '--network none' when starting the container, which removes any route to the outside world at the kernel level. Even if malicious code tries to open a socket, there is simply no network path available. The worker communicates with the container through mounted volumes or stdin/stdout pipes instead, so a network interface is never needed.
    2. When scaling workers based on queue depth, the threshold for triggering scale-up should be relative to current worker throughput, not a fixed message count. For example, 100 queued messages is a crisis if workers drain 1 per second but totally fine if they drain 50 per second. A better signal is something like queue depth divided by drain rate, which tells you how many seconds of backlog you actually have.
    3. For SSE-based live leaderboards under bursty traffic, avoid pushing a full leaderboard snapshot on every single score change. Instead, batch or throttle updates on a short interval such as every 1 to 2 seconds. This prevents a flood of submissions from causing a fanout storm where thousands of open SSE connections all receive rapid-fire updates simultaneously.
