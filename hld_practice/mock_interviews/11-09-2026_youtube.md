# Feedback notes

## 1. Adaptive Bitrate Streaming (ABR)

- **ABR = Adaptive Bitrate**.
- ABR logic runs on the **client/player**.
- Client monitors:
  - Actual **segment/chunk download throughput**
  - **Playback buffer health**
- It chooses the quality of the **next segment**.
- If network degrades → switch to lower bitrate/quality.
- If network improves → switch to higher quality.
- The goal is **smooth playback with minimal buffering**, not maximum quality at all times.

## 2. HLS vs DASH

Both are **adaptive streaming protocols/formats** used to deliver video as small segments.

| | HLS | DASH |
|---|---|---|
| Manifest | **M3U8** | **MPD** |
| Purpose | Describes available streams/segments | Describes available streams/segments |
| Actual video | Separate media segments | Separate media segments |

### Important
- HLS/DASH **do not decide the quality**.
- **ABR decides** which representation/quality to request.
- HLS/DASH provide the structure and metadata needed by the player.

## 3. Manifest File

Think of the manifest as a **map/catalog of the video**.

It can describe:

- Available resolutions/bitrates: 360p, 480p, 720p, 1080p, 2K, 4K, etc.
- Segment/chunk information
- Segment duration/timing
- Locations/URLs from which segments can be fetched
- Different encoded representations

### Important correction
The manifest **does NOT contain the actual video chunks**.

Also, don't say it is necessarily JSON.

Better interview wording:

> “The manifest describes the available representations and the segments/locations needed to fetch them.”

### Flow

`Manifest → ABR chooses representation → Client requests segment → CDN serves segment`


## 4. CDN + Origin Storage

### Origin
Durable source of the video, e.g. object storage such as S3.

### CDN
Caches video **segments** close to users for fast delivery.

Important mental model:

`Origin Storage → CDN Edge → Client`

### What happens for an old/unpopular video?

The entire video does **not need to permanently exist in every CDN cache**.

If a requested segment is not cached:

1. Client requests segment from CDN.
2. CDN has a **cache miss**.
3. CDN fetches that segment from origin.
4. CDN serves it to the client.
5. CDN may cache that segment for future requests.

CDNs can also use **prefetching**, but don't assume that the CDN always downloads the entire video in advance.

### Interview line
> “Origin storage is the source of truth; CDN edges cache segments based on demand and eviction policies.”


## 5. Playback Resume / Watch Progress

Example:

User watches a 6-minute video until **2:00 on phone**, closes YouTube, then opens the same video on laptop.

Laptop should resume around **2:00**.

There are two main flows:

### Write Path

Client periodically checkpoints playback progress.

Example:

`User → Phone → Playback Progress Service → Database`

Store something like:

```text
userId + videoId → lastPosition
```

Example:

```text
(user123, video456) → 120 seconds
```

Don't write every millisecond/second forever.

Typical approach:

- Periodic checkpoint every few seconds
- Also checkpoint on pause/exit when possible
- If the phone suddenly dies, losing a few seconds is acceptable

### Read Path

When user opens the video on another device:

`Laptop → Playback Progress Service → Database → lastPosition`

Then:

`Video starts from saved position`


## 6. Where to Store Playback Progress?

Use a **scalable persistent key-value / NoSQL datastore** as the source of truth.

Example conceptual choices:

- DynamoDB
- Cassandra
- Bigtable
- Other distributed KV/NoSQL store

The exact database is less important than explaining the access pattern.

### Key

`(userId, videoId)`

### Value

```text
lastPosition
updatedAt / version
```

Example:

```text
user123 + video456
        ↓
position = 120 sec
version  = 42
```

#### Cache?

A cache such as Redis can optionally accelerate **hot reads**, but don't make an ephemeral cache the only durable source of truth.


## 7. Handling Out-of-Order / Retry Writes

Network retries can cause an **older update to arrive after a newer update**.

Example:

```text
Update A → 100 sec
Update B → 120 sec
```

If B arrives first and A arrives later, A must not overwrite 120.

Use:

- Timestamp/version/sequence number
- Accept the newer version
- Reject stale updates

### Interview line

> “We attach a timestamp or monotonically increasing version to progress updates so delayed retries cannot overwrite a newer position.”

## 9. Summary

> “For video delivery, we use HLS or DASH to describe and deliver video in segments. The manifest describes the available representations and segment locations, while the client-side ABR algorithm monitors throughput and buffer health and selects the appropriate quality for the next segment. The CDN caches segments close to users, with origin storage as the source of truth. For playback resume, the client periodically checkpoints the user's position using a scalable persistent key-value store keyed by user and video ID. When the user switches devices, the new device reads the saved position and resumes playback. We use timestamps or versions to prevent stale retry updates from overwriting newer progress.”
