## Feedback

1. **Requirements**
    1. For file sync systems like Dropbox, prioritize availability over strict consistency. Devices can briefly show slightly outdated data as long as they eventually converge to the same state. This is called eventual consistency and is the right tradeoff when uploads must never be blocked.
    2. Large file uploads need chunked uploading so that if a network interruption happens, the upload can resume from the last successful chunk rather than starting over. This is critical for Dropbox-style systems where files can be gigabytes in size.
2. **Core Entities**
    1. For file sync systems like Dropbox, always include Devices as a separate entity from Users. One user owns many devices, and the sync state can differ per device, so tracking them separately is essential for modeling which device has which version of a file.
3. **API**
    1. For sync-based systems, always include a 'changed_since' filter on your list endpoint, like GET /files?changed_since=<timestamp>. This lets devices fetch only what changed since their last check instead of downloading everything, which is how real sync works.
    2. In REST design, resource identifiers belong in the URL path, not the request body. Use PUT /files/{file_id} instead of sending file_id in the body. This makes it unambiguous which resource is being updated and follows standard REST conventions.
    3. Pagination needs two things to work end to end. A page_size parameter controls how many results come back, but you also need a cursor or page token in the response so the client knows how to request the next batch. Without the cursor, the client has no way to continue walking through results.
4. **High Level Design**
    1. After a device downloads a synced file, the sync agent must do two things to close the loop: write the file into the local sync folder and update the local metadata store. If you skip mentioning the local metadata update, your design leaves open the question of how the client avoids re-downloading the same file on the next sync cycle.
    2. When a server notifies a client that a file changed, be explicit that the client then makes a follow-up request like a get changes or fetch metadata call using the file ID. This distinction matters because it separates the notification step from the data fetch step, making the control flow clear and showing you understand the client is pulling specific data rather than just receiving a vague push event.
    3. For a CDN plus blob storage download setup, state explicitly how the client chooses between them. A simple rule to memorize is that the client tries CDN first for cached content and falls back to blob storage if the CDN does not have it. This shows you understand CDN as a cache layer in front of origin storage, not just an alternative to it.
    4. When describing a file sync client, say it primarily uses OS-level file change notifications (like inotify on Linux or FSEvents on macOS) and falls back to periodic polling as a backup. This is better than leading with periodic polling because OS notifications are event-driven, meaning the client reacts immediately and avoids wasting CPU scanning files that have not changed.
5. **Deep Dives**
    1. Before marking a file upload as complete, the server must verify that every expected ***chunk index*** from 1 to N is present exactly once. This finalization check prevents corrupted uploads where a chunk is missing or duplicated from being silently committed.
    2. Each chunk in a resumable upload should be stored by its exact index position in the upload session. Duplicate uploads for the same index should overwrite only that slot, not shift other chunks. This keeps chunk identity and chunk order separate and safe.
    3. Use a ***checksum*** or ***hash*** per chunk so the server can validate that the correct data was uploaded for each position, not just that something arrived. Without this, a chunk at index 3 could contain garbage bytes and the server would have no way to detect it before finalizing.
    4. For delta sync on large files, ***chunk hashes are the fingerprinting mechanism*** that tells you which chunks actually changed. When a file is edited, the client computes hashes for each chunk and compares them to the stored manifest. Only chunks with different hashes need to be uploaded or downloaded.
