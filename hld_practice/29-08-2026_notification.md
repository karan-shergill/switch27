# Feedback

1. **Requirements**
    1. Notification traffic is bursty, not steady. Large campaigns send millions of messages in a short window, creating spikes up to 50x the normal sustained rate. A good NFR statement anchors this with a concrete number like 5,000 notifications per second at peak, and explicitly says the system should degrade gracefully rather than drop messages.
    2. At-least-once delivery means duplicates are acceptable but drops are not. State this distinction explicitly in interviews because it directly drives design decisions like using durable queues with retries and idempotency keys on the consumer side.
    3. Critical notifications like OTPs and fraud alerts need a concrete latency target, not just a vague priority label. A good target to memorize is under 5 seconds from acceptance to delivery, even during a surge. Without a number, the requirement gives the system no measurable goal to design toward.
2. **High Level Design**
    1. For async work like scheduled notifications or campaign fan-out, return an HTTP 202 Accepted response instead of 200 OK. This signals to the caller that the request was accepted but not yet completed, making the API contract honest about what actually happened.
    2. When designing a campaign blast system, store the campaign as its own separate record with metadata like segment ID, send time, and status. Then at fan-out time, expand the segment into individual per-user notification records. Mixing campaign-level data with per-user notification records in the same table creates confusion about ownership and makes the data flow hard to reason about.
    3. Push notifications are delivered via APNs (Apple Push Notification service) for iOS and FCM (Firebase Cloud Messaging) for Android. These are external provider integrations, not internal services you build. Naming them explicitly in a design keeps your platform boundary clear and shows you understand the last-mile delivery layer.
    4. When a notification is suppressed due to user preferences or quiet hours, still write a record to your notifications table with a status like 'not_sent_user_preference'. This preserves auditability so you can answer questions like 'why did this user not receive this notification' without the send silently disappearing.
3. **Deep Dives**
    1. The transactional outbox pattern solves the write-then-publish atomicity problem. Instead of writing a record to your DB and then publishing to a queue as two separate steps, write both the record and an outbox row in a single DB transaction. A separate relay process reads committed outbox rows and publishes them to the queue. A crash before commit loses both safely, and a crash after commit means the relay will eventually publish. This eliminates the window where a record exists but no queue message does.
        1. We have a dual-write problem because persisting the notification and publishing to Kafka are two independent operations. If the service crashes after the DB commit but before publishing, the notification can be stranded.
        2. I'd use the transactional outbox pattern. In the same DB transaction, I'd write both the notification record and an outbox event. Once that transaction commits, we've durably accepted the work. A separate outbox relay, either polling the table or using CDC, publishes committed events to Kafka.
        3. The relay can publish duplicates if it crashes after publishing but before marking the outbox event processed, so I'd assume at-least-once delivery and make downstream processing idempotent using an event or notification ID.
        4. In single sentence: Transactional Outbox converts an unsafe DB + queue dual write into an atomic DB + DB write, then reliably bridges the outbox to the queue asynchronously with retries; duplicates are handled through idempotency.
    2. Parallelizing two non-atomic operations does not make them atomic. If you write to DB and publish to a queue at the same time, a crash after one completes still leaves the system in a broken state. Parallelism reduces latency but gives you zero durability guarantees across two separate systems. Atomicity requires a shared transaction boundary, not simultaneous execution.
    3. Dedup for notifications requires a stable deterministic identity that survives retries. A good dedup key is something like campaign ID plus recipient ID, or a caller-supplied idempotency key. The flow is: check for an existing outcome before sending, then write the dedup marker only after the provider acknowledges success. This way a crashed worker that retries will find the existing record and skip the send, avoiding duplicates without silently dropping notifications.
        1. Because delivery is at-least-once, every notification needs a stable idempotency key, such as a notification ID, or campaign ID plus recipient ID. The consumer maintains a durable delivery record and atomically claims work so concurrent workers don't send the same notification.
        2. However, there's a crash window after the provider accepts the message but before we persist SENT. Therefore, a DB dedup record alone cannot guarantee exactly-once side effects with an external provider. Ideally the downstream provider supports idempotency keys, and we send the same key on retries. If it doesn't, we have to choose between potential duplicates and potential drops for that ambiguity window, and make the trade-off explicit.
    4. Isolating internal queues and worker pools is not enough to protect critical traffic from bulk traffic. Bulk sends can exhaust your provider's rate limit budget, meaning your OTP gets throttled at the Twilio or FCM boundary even if it reached the front of your internal queue instantly. The fix is to reserve a portion of each provider's send rate budget specifically for critical traffic so bulk campaigns cannot spend it first.
