# Feedback

1. **Requirements**
    1. Fault tolerance is a must-have non-functional requirement for any large-scale messaging system. Servers will fail regularly at WhatsApp's scale, so your requirements should explicitly state that the system must continue operating correctly even when individual servers or services go down. Without this, you risk losing messages or dropping connections during failures.
    2. Message persistence in a messaging system should be temporary by design. Once a message is delivered to the recipient, it does not need to live on the server indefinitely. This is both a privacy consideration and an architectural one, since storing messages only as long as needed reduces storage costs and aligns with how products like WhatsApp actually work.
2. **High Level Design**
    1. Kafka is a streaming system, not a queryable inbox. Once a consumer reads a message from Kafka, it is gone from that consumer's perspective. For offline delivery in chat, you need a separate persistent store with records per recipient so you can query 'what messages does this user still need to receive' when they reconnect.
    2. A clean separation for chat delivery is: Kafka handles real-time fanout to online users through chat servers, while a persistent offline store handles missed messages for users who were disconnected. The chat server checks connection state first, delivers immediately if online, and writes to the offline store if not.
    3. For media in a chat system, have the client request a pre-signed URL from the chat service and upload directly to S3. Then store only a lightweight reference like a CDN URL, media type, and size in the message metadata. This keeps large binary data off your chat servers entirely and lets receivers fetch media separately through the CDN.
3. **Deep Dives**
    1. When you have multiple chat servers handling WebSocket connections, you need an explicit user-to-server registry (like Redis or Zookeeper) that maps each connected user to the specific server holding their connection. Without this, servers have no way to route an incoming message to the right destination. Just adding more servers does not solve delivery, it makes it harder without a source of truth for where each user is connected.
    2. In a multi-device chat system, delivery state should be tracked per client, not per user. One user may have a phone, laptop, and web browser connected. Each device needs its own delivery record so that when a device reconnects after being offline, the system knows exactly which messages that specific device missed and needs to receive.
    3. Each active device session for a user should have its own unique session or client identifier stored in the user record as a list. When routing a message, the system fans out to every client ID for that user, targeting each active WebSocket connection separately. This is what keeps all devices in sync rather than treating them as one generic recipient.
