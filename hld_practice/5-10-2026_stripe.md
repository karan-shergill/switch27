## Feedback

1. **Requirements**
    1. Payment systems require an audit trail as a core requirement, not just durability. Every transaction and every state change must be permanently recorded so the system can support compliance rules, reconciliation, and dispute investigations. Saying 'no transaction is dropped' is not enough on its own.
    2. In a payment system, both sides of the transaction need authentication and protection. Customer card data must be encrypted and handled securely, and merchant credentials must also be authenticated to prevent unauthorized API access.
    3. For availability requirements in financial systems, attach a specific number like 99.99% uptime rather than just saying 'high availability'. This translates to roughly 52 minutes of downtime per year and gives your design a concrete target to build against with redundancy and failover strategies.
2. **Core Entities**
    1. In a payments system, Payment Intent is the central entity that tracks the full lifecycle of a single attempt to collect money, including its status (pending, succeeded, failed). It ties together the merchant, the amount, and the outcome in one place.
    2. Merchant represents the business receiving money and is a top-level entity in payment systems. Separating Merchant from Transaction lets you model one merchant having many transactions over time without duplicating business details.
    3. Transaction captures individual money movements like charges, refunds, and payouts. Keeping these as separate records (rather than updating one record) gives you a full audit trail, which is critical in financial systems for debugging and compliance.
3. **API**
    1. A payment API needs separate endpoints for each actor. The customer submits card details and gets immediate transaction status, but the merchant also needs a way to check payment status later, either through a GET endpoint like GET /payment-intents/{id} or through webhooks that push status updates to the merchant server.
4. **High Level Design**
    1. A PaymentIntent should have an explicit initial status of 'created' when first saved. This matters because the status field is how your system communicates where in the lifecycle a payment is, and 'created' signals that no charge has been attempted yet. Always name the starting state explicitly in your design.
    2. The relationship between a PaymentIntent and a Transaction is that the intent represents what the customer wants to pay, and the transaction represents a specific attempt to collect that payment. When processing a charge, your payment service should look up the PaymentIntent to get the expected amount and currency, then create a transaction record linked to that intent. ⭐️
    3. When describing a status read API in an interview, be explicit about the shape of the call. A merchant calls a GET endpoint with a PaymentIntent ID or transaction ID and receives back the current status plus relevant details like amount and currency. Stating this concretely shows you understand the API contract, not just the concept.
    4. Only the merchant who owns a PaymentIntent should be allowed to fetch its status. In an interview, briefly calling out this authorization check shows you are thinking about multi-tenant security, which is critical in payment systems where one merchant must never see another merchant's payment data. ⭐️
5. **Deep Dives**
    1. Request signing with a timestamp and nonce is how you prevent replay and tampering attacks on payment APIs. The merchant signs the request body plus a timestamp using their private secret, and your server verifies the signature, rejects requests outside a small time window (like 5 minutes), and checks a nonce store to block replayed requests. A static API key alone cannot do this because it proves identity but not that the request body was unmodified. ⭐️
        1. For merchant authentication, I would use API credentials combined with request signing.
            1. API key → Who are you?
            2. Signature → Did you actually send this exact request?
            3. Timestamp + nonce → Is this request fresh, or is someone replaying an old one?
        2. Each merchant gets a unique credential/secret. For every payment API request, the merchant generates a signature over a canonical representation of the request, including the HTTP method, path, request body hash, timestamp, and a unique nonce.
            1. `signature = HMAC-SHA256(merchant_secret, method + path + body_hash + timestamp + nonce)` 
        3. The timestamp and nonce protect against replay attacks, while signing the request body protects against tampering. A static API key alone identifies the merchant, but it doesn't provide request-level integrity or replay protection.
    2. For card data encryption in the browser, use asymmetric encryption. The browser encrypts card data with your backend's public key, and only your backend can decrypt it using the paired private key stored in an HSM. A shared symmetric secret is harder to distribute safely and harder to protect. The HSM detail matters because it means raw card data is never decrypted in normal application memory. ⭐️
    3. Tamper-evident audit logs require three things working together. First, use write-once-read-many storage with retention locks on S3 and append-only Kafka topics with ACLs so no one can delete or overwrite events. Second, separate duties so database operators cannot administer the audit store. Third, compute cryptographic hashes or signatures over events and publish periodic digests to a location operators cannot reach, so an auditor can recompute hashes and prove nothing was altered.
        1. The key ideas are **immutable storage, restricted access, and cryptographic verification**.
    4. When two writers race to update a payment status, use optimistic locking to resolve it safely. Each row has a version number, and a writer must pass the current version in its update. If another writer already incremented the version, the compare-and-set fails, the losing writer re-reads the row, and then retries or discards its stale update. You also need to enforce a valid state machine (pending to success or failed) and compare event timestamps from the gateway so you never apply a backward transition.
