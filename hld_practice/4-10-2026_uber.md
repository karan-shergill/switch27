## Feedback

1. **Requirements**
    1. Ride-sharing systems must explicitly call out burst/surge handling as a non-functional requirement. At peak hours or events, tens of thousands of requests can flood in from the same area at once. Dropping these requests is unacceptable, so the system needs queuing (to buffer requests) and location-based partitioning (to distribute load). Naming this upfront signals you understand real-world traffic patterns.
    2. For ride matching, label the guarantee as strong consistency, not just high availability. These two properties can conflict under concurrent requests. If two drivers both try to accept the same rider, only one can win. Strong consistency ensures correctness here, and it is worth explicitly stating that consistency takes priority over availability for the matching operation.
2. **API**
    1. Use PATCH instead of POST when updating an existing resource. POST creates something new, PATCH modifies it. For example, a driver accepting a ride changes the state of an existing ride, so it should be PATCH /rides/{rideId} with a body like {status: 'accepted'}, not POST to a new endpoint.
    2. A POST endpoint that creates a resource should return the newly created resource in the response, not just a bare 202. For a ride request, return the ride_id and status so the client has something to track and poll against.
    3. In a ride-sharing system, drivers need a dedicated endpoint to continuously send their GPS position so the backend knows who is nearby when matching. A simple POST /drivers/location with a body of {lat, long} returning a success or failure covers this requirement.
    4. When two different IDs share the same URL pattern like POST /ride/{id}, the server cannot tell which type of resource the ID refers to. Separate them by using distinct paths and HTTP verbs, for example POST /rides to create a ride with an estimate_id in the body, and PATCH /rides/{rideId} to update it.
3. **High Level Design**
    1. When using a third party maps provider in a ride sharing design, be specific about what you are requesting from it. You need route, distance, and ETA between two points, not live location data. Saying 'live location' is vague and confusing because that implies tracking, not routing.
    2. When a rider accepts a fare estimate, the first thing your Trip Request Service should do is validate the estimate ID and confirm the selected cab type and fare match what was stored. This prevents stale or tampered estimates from creating bad trip records and is a quick thing to call out explicitly in an interview. ⭐️
    3. When matching a rider to a driver, always filter your candidate pool by availability status before ranking by distance. Querying Redis for nearby drivers and then offering the ride to unavailable drivers wastes time and makes your matching logic look incomplete. The correct order is filter by available status first, then rank by proximity or cab type.
    4. When notifying a driver about a ride, be explicit that the minimum payload they need is the pickup coordinates, the fare, and the cab type. Saying 'trip details' is too vague in an interview. Calling out the specific fields shows you understand what data drives the driver's decision to accept or decline.
4. **Deep Dives**
    1. For real-time location tracking at scale, keep active driver locations in an in-memory geospatial store like Redis with the GeoSearch command. This gives you fast writes and fast proximity queries without hitting a traditional database. GeoHash is useful as an indexing and partitioning strategy, not for computing exact distances directly. ⭐️
    2. In a distributed matching system, sending requests to drivers one at a time within a single worker does not prevent two workers from sending the same driver two different ride requests at the same time. You need a shared atomic state per driver, for example a database field or distributed lock that transitions the driver from 'available' to 'pending_request' atomically before notifying them. Any worker that cannot claim that state skips the driver. ⭐️
    3. A queue only protects you from losing messages if you acknowledge the message only after the matching result is successfully persisted. Without this, a worker crash after picking a message but before saving state means the message is gone and the ride request disappears. Use a visibility timeout or explicit acknowledgment so unfinished messages are redelivered to another worker automatically.
    4. When a retry worker picks up a crashed worker's trip, it should not restart the driver notification list from scratch. Instead, record which drivers were already contacted and their outcomes on the trip record itself. The retry worker can then resume from where the crash happened, which preserves your at-most-one-request-per-driver guarantee and avoids sending duplicate requests to drivers who already responded ⭐️
