## Feedback

1. **Requirements**
    1. Time to first token is the most important latency metric for LLM chat products because streaming responses make the product feel fast even when total generation takes several seconds. Users perceive responsiveness from when text starts appearing, not when it finishes.
    2. For chat applications, favor availability over consistency using CAP theorem framing. Conversation state being slightly out of sync across replicas is acceptable, but the service going down is not. This is the right tradeoff to call out explicitly in interviews.
    3. Anchor your scale estimates to a concrete DAU number and derive QPS from it. For example, 200M DAU with average usage patterns translates to roughly 20k prompts per second, which then drives decisions about caching, sharding, and compute capacity.
2. **API**
    1. REST API resource names should always be plural and consistent across all endpoints. Use /chats and /chats/{chat_id}/messages everywhere, not a mix of /chat and /chats or /message and /messages. Consistency makes APIs predictable and easier to use.
    2. Paginated list responses should return an array wrapped in an object, like { items: [...], next_cursor: '...' }. This gives the client a clear structure to iterate through pages and know when there are no more results.
    3. User identity in REST APIs should come from an auth token or header (like Authorization: Bearer <token>), not from the URL or request body. This keeps user IDs out of the API surface and lets the server resolve identity securely on the backend.
3. **High Level Design**
    1. When you store user messages and model outputs in separate tables, you need a shared ordering mechanism like a timestamp or sequence number to reconstruct conversation history in the correct turn order. Without this, you cannot reliably build the prompt for the next model call or display the chat history to the user.
    2. When continuing a conversation, the chat service should explicitly concatenate all prior turns in role order (user, assistant, user, assistant...) and append the new user message before sending to the model worker. This is how the model gets context about what was said before, and stating it plainly in an interview makes your design unambiguous. ⭐️
    3. Name your read API endpoints explicitly in your design walkthrough. For a chat system, the two key read paths are list chats (returns all conversations for a user) and get messages (returns all turns for a specific chat). Naming them connects your data model to the actual user experience and makes your design easier to evaluate.
4. **Deep Dives**
    1. When streaming LLM tokens over SSE, you must handle the case where a worker crashes before sending a terminal event. The chat server should apply an inactivity timeout since the last received token as a fallback, then send the client an error event, close the SSE stream, and mark the run as failed or partial in the database. Without this, a crashed worker leaves the SSE connection open forever.
    2. GPU inference workers should batch multiple queued prompts together rather than processing one at a time. Batching keeps the GPU busier because matrix operations on the GPU are most efficient when parallelized across multiple inputs at once. This is the primary GPU-specific optimization in LLM serving and directly reduces cost per request.
    3. Token-based rate limiting for LLM requests is tricky because the true output token count is only known after generation completes. The correct pattern is to estimate cost at admission time using input token count plus a capped max output allowance, reserve that amount atomically in Redis, and then reconcile when the run finishes by refunding unused tokens or debiting overages. This prevents users from bypassing limits by sending many concurrent requests before any one finishes.
    4. When using Kafka to fan out tokens from a worker to the chat server, key messages by run_id so all tokens for a run land in the same partition. This preserves ordering on the wire. Then attach a monotonically increasing token index to each message so the chat server can detect gaps or duplicates even if messages arrive slightly out of order.
